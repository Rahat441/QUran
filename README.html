What this project does

Quran Research Assistant is a local Retrieval-Augmented Generation application. It does not ask a language model to recall Quran verses from memory. Instead, it maintains a verse-level local database, searches that database for evidence, and supplies the retrieved verses to a local Ollama language model for explanation.

What it is

A verse discovery and research aid that returns Quran evidence, citations, and an AI-generated explanation.

What it is not

An Islamic authority, scholar, fatwa service, tafsir replacement, or guarantee that every relevant verse has been found.

How every application script contributes

cli.py

Terminal entry point

Defines every quran-ra command, prints Rich tables, handles interactive chat, and converts operational exceptions into readable terminal errors.

config.py

Configuration boundary

Reads .env and QRA_* environment variables with Pydantic, supplies defaults, and validates numeric limits before services start.

models.py

Trusted domain objects

Defines a validated Verse, canonical surah:ayah reference, searchable document text, Chroma metadata, and scored SearchResult.

quranlab.py

Reproducible source importer

Downloads a pinned QuranLab revision, joins Arabic and English by verse key, preserves provenance, validates all 6,236 records, and atomically writes quran.json.

loader.py

Dataset normalization

Accepts JSON arrays, wrapped JSON, or JSONL; understands common field aliases; validates records; and rejects duplicate references before indexing.

embeddings.py

Local semantic representation

Wraps the Ollama embedding endpoint. It turns verse documents and user questions into vectors using the configured local embedding model.

store.py

Persistent vector storage

Creates the Chroma collection, embeds verse batches during ingestion, stores exact metadata, and performs cosine-similarity searches.

retrieval.py

Candidate ranking

Requests semantic candidates from Chroma, measures English/Arabic token overlap, combines both scores, and returns the configured top results.

generation.py

Evidence prompt and LLM call

Serializes retrieved citations, Arabic, translations, and scores; adds strict evidence-only instructions; then requests a zero-temperature Ollama answer.

service.py

Application orchestrator

Constructs the embedder, Chroma store, retriever, and generator. It also applies the minimum relevance threshold before allowing generation.

__init__.py

Package identity

Marks the source directory as the quran_assistant package and exposes the application version.

tests/test_*.py

Automated checks

Verify loader aliases, duplicate rejection, verse behavior, QuranLab count validation, and basic lexical relevance scoring.

Prerequisites and installation
  • Python 3.12+ runs the package and CLI.
  • Ollama hosts both local models.
  • Internet access during setup downloads dependencies, models, and QuranLab source files.
  • Approximately 6 GB of model storage is needed for the selected embedding and generation models.
python3.12 -m venv .venv
source .venv/bin/activate
pip install -e '.[data,dev]'
cp .env.example .env
ollama pull nomic-embed-text
ollama pull qwen2.5:7b
quran-ra doctor

.[data] adds PyArrow for QuranLab Parquet conversion. .[dev] adds pytest, Ruff, mypy, and coverage tooling.

Quran dataset, fields, and provenance

quran-ra fetch-data downloads two pinned QuranLab configurations:

  • arabic-uthmani: Tanzil Uthmani version 1.1, CC BY 3.0, retained verbatim.
  • en-pickthall: Marmaduke Pickthall's 1930 public-domain English translation.

The importer joins them using QuranLab's canonical verse_key, validates exactly 6,236 unique verses, and writes source and license metadata at the top of the generated file.

{
  "surah_number": 1,
  "surah_name": "Al-Faatiha",
  "ayah_number": 1,
  "arabic": "بِسْمِ ٱللَّهِ ٱلرَّحْمَٰنِ ٱلرَّحِيمِ",
  "translation": "In the name of Allah, the Beneficent, the Merciful",
  "transliteration": "",
  "juz": 1,
  "revelation_type": "Meccan"
}

The current QuranLab combination does not include transliteration, so that field is intentionally empty. The application also accepts custom JSON arrays, {"verses": [...]} objects, or JSONL records.

What is embedded and stored

Each verse becomes one searchable document containing:

  1. Surah name and canonical reference
  2. English translation
  3. Transliteration when available
  4. Arabic Quran text

Ollama embeds that combined document. Chroma stores the resulting vector plus exact metadata: surah number, surah name, ayah number, Arabic, translation, transliteration, Juz, and revelation type.

Ingestion uses batches of 128 verses and upserts each verse under its canonical ID, such as 2:255.

Every CLI command
quran-ra doctor

Checks the Ollama connection, reports whether both configured models exist, and prints the indexed verse count.

quran-ra fetch-data

Downloads the pinned QuranLab files and writes a validated data/quran.json. Use -o to choose another output.

quran-ra ingest data/quran.json

Loads, validates, embeds, and upserts every verse into ChromaDB. This is the slow setup stage.

quran-ra search "question"

Runs retrieval only and prints scores, references, surah names, and translations. Useful for debugging evidence.

quran-ra ask "question"

Retrieves evidence, checks the top score, and requests a grounded explanation from the configured LLM.

quran-ra chat

Creates the assistant once and accepts repeated questions until quit or exit.

quran-ra doctor
quran-ra fetch-data
quran-ra ingest data/quran.json
quran-ra search "patience during trials"
quran-ra ask "What does the Quran say about mercy?"
quran-ra chat
Answer format and grounding behavior

The system prompt requests these sections:

  1. Question
  2. Summary Answer
  3. Primary Evidence
  4. Additional Relevant Verses
  5. Reasoning (AI explanation)
  6. Confidence

Every retrieved evidence block includes its reference, surah name, Arabic, English translation, and retrieval score. Temperature is set to zero to reduce variation.

If no candidates exist or the best score is below QRA_MINIMUM_RELEVANCE, the service returns:

I could not find sufficient Quranic evidence to confidently answer this question.
Current V1 behavior: grounding is enforced by prompting, but generated citations and quoted text are not yet programmatically validated. Deterministic rendering and citation allowlisting are planned before acceptance release.

export PATH="/usr/local/bin:$PATH"
open -a Ollama
/usr/local/bin/ollama list

Ollama connection failed

Open the Ollama application or run ollama serve, then confirm QRA_OLLAMA_HOST points to the active service.

Model is missing

ollama pull nomic-embed-text
ollama pull qwen2.5:7b
quran-ra doctor

Indexed verses is zero

quran-ra fetch-data
quran-ra ingest data/quran.json
quran-ra doctor

Search results seem stale after changing data or models

Remove or move the local data/chroma/ index and ingest again. A safer built-in rebuild command is planned.

Current V1 limitations and planned hardening
  • Grounding: evidence-only behavior is currently prompt-based; citations and copied Quran text need deterministic validation.
  • Hybrid search: lexical scoring currently reranks only semantic candidates; independent full-corpus BM25 is planned.
  • Exhaustive questions: default output is eight verses, so “show every verse” is not yet a true exhaustive mode.
  • Confidence: the current threshold is a configurable heuristic and still needs calibration against reviewed questions.
  • Index identity: Chroma does not yet record the dataset fingerprint and embedding model together.
  • Tests: generation, service, CLI, and full retrieval integration need broader automated coverage.
  • Translation: Pickthall is public domain but uses older English; multiple translations are intentionally deferred.
  • Transliteration: the selected QuranLab configurations do not supply it.

Planned order: deterministic output → true hybrid retrieval → reviewed regression set → calibrated confidence → index fingerprints → expanded acceptance tests.

Future architecture boundaries

The source layout deliberately separates domain models, ingestion, embeddings, storage, retrieval, generation, orchestration, and interface code. That allows future modules to be added without rewriting the core workflow.

  • Multiple Quran translations
  • Tafsir collections with separate provenance
  • Hadith retrieval in an independent collection
  • Scholar comparison
  • Arabic root and morphology analysis
  • Notes and bookmarks
  • A web interface using the same service layer

These are extension points only; they are not implemented in V1.
